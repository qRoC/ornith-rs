# Moving this port to an M5

`HANDOFF.md` is the source of truth for what the port is and what it measures.
This is the sheet for one event: the day it runs on a GPU where
`nax_available()` is true. Everything here is read out of `../vendor/mlx` at
the commit this port was written against, with file and line, so it can be
checked rather than believed.

**The headline, and it is not what the kernel names suggest: NAX is a prefill
lever, not a decode one.** Every route into the `*_nax` kernels is guarded by a
width or a length that a decode step does not have. Sections 2 and 3 are the
proof of that, one condition at a time. What an M5 changes for decode is
elsewhere -- and smaller.

---

## 1. The tripwires

The port asserts its way into this rather than discovering it in a number.
`Context::nax_available()` (`src/metal/mod.rs:553`) is mlx's
`metal::is_nax_available()`: architecture generation >= 17, or >= 18 on a `p`
part. Five asserts fire the first time it is true:

| | |
|---|---|
| `src/ops/quantized.rs:202` | the quantized gemm |
| `src/ops/quantized.rs:293` | the qmm path's guard |
| `src/ops/quantized.rs:415` | the gather gemm |
| `src/ops/matmul.rs:102` | the dense gemm |
| `src/ops/sdpa.rs:304` | full attention |

`tests/quantized.rs::dispatch_choices_for_this_model` skips itself off gen 16
and says so; it is the test to re-pin first.

None of these mean the port is wrong on an M5. They mean mlx would now pick a
kernel this port does not carry, so the divergence becomes a decision instead
of an accident. Running on an M5 with them removed and nothing else done gives
the same answers, more slowly than mlx.

---

## 2. Why decode does not reach the NAX kernels

**The quantized gemm.** `qmm`'s NAX branch is
`is_nax_available() && (transpose || mode == "affine")`, with alignment
`K % 64 == 0 && (transpose || N % 64 == 0)`, and a dtype that is not float32
unless tf32 is enabled (`quantized.cpp:1059`). This port's weights are
transposed affine with K a multiple of 64 and bfloat16 activations, so the
branch would be taken -- **if it were reached**. It is reached only from

```cpp
int vector_limit = transpose_ ? get_qmv_batch_limit(K, N, d) : 4;
if (M >= vector_limit) { qmm(...); }      // quantized.cpp:1885
```

and below that limit the dispatch goes to `qmv`, which **has no NAX variant at
all**. A decode step is M = 1 against a limit of 13 to 33. So the 195 `qmv`
dispatches that are 38% of a decode step's time do not change.

**The routed experts.** `gather_qmm`'s NAX branch wants
`is_nax_available() && transpose && K % 64 == 0` (`quantized.cpp:1279`), and
`gather_qmm_rhs`'s wants only `is_nax_available() && transpose`
(`quantized.cpp:1674`) -- no alignment condition, which makes it the most
reachable of the three. But the rhs-sorted path is entered at M = 1 only when

```cpp
if (M == 1 && B >= 16 && right_sorted_ == true && B / E >= 4)   // quantized.cpp:1991
```

and this model decodes one token into top-8 of 256 experts: B = 8, E = 256, so
`B >= 16` is false and `B / E` is 0. Both fail. This is the same arithmetic
that already rules out forcing the sorted gather for an MTP verify window (see
HANDOFF, "It does not pay off here"); the conditions are the port's own
`gather_qmm_rows`, at `src/ops/quantized.rs:334`.

**Attention.** `sdpa_full_self_attention_nax` takes head dims 64, 96, 128 or
256 (`scaled_dot_product_attention.cpp:218`). This model's text head_dim is
**256**, so it qualifies -- but it is the *full* self-attention path, the one a
prompt takes. A decode step has one query row and goes to the vector path,
which has no NAX form.

So the decode step, which is what this port's whole performance story is about,
gains nothing directly from NAX.

## 3. What an M5 does change

In rough order of how much it is likely to be worth here.

**Prefill, through three doors.** A prompt chunk is 2048 rows, far above every
vector limit, so the quantized gemm, the expert gather and full attention all
take their NAX forms at once. This port's prefill is 2.05-2.34 s of GPU busy
for 2600 tokens (HANDOFF, "The prompt"), and that is the number an M5 would
move. Whether it moves it *usefully* is a separate question: the wall there is
currently 33-49% idle from memory pressure, so a faster prefill on a swapping
machine buys less than it looks.

**The gated-delta recurrence.** Not a `*_nax` matmul but keyed off the same
flag: the chunk size doubles.

```cpp
if (T >= threshold) C = metal::is_nax_available() ? 16 : 8;   // gated_delta_update.cpp:82
if (!metal::is_nax_available()) C = std::min(C, 8);           // ...:89
```

`threshold` is 16 by default (`GATED_DELTA_THRESH`), so this too is a prompt
change and not a decode one -- but 30 of this model's 40 layers are
gated-delta, which makes it the largest single prefill item. mlx carries
`gated_delta_update_fused_nax.metal` for it; this port carries the packed
non-NAX kernel and would need the other.

**The vision tower, for free-ish.** Its head_dim is 72, which the NAX path does
not take, but mlx pads 72 and 80 to 96 to reach it
(`scaled_dot_product_attention.cpp:239`), on by default for
`qL >= 512 && kL >= 512` unmasked half-precision attention. A 48x48 patch grid
clears that. The pad and the output copy are the cost; the tower runs once per
image rather than once per token, so this is a convenience, not a lever.

**The qmv batch limits move, which matters only in a band.**

```cpp
if (arch_gen >= 17 && arch_size != 'd') {
  if (D <= 2048 && O <= 2048) return 33;
  else if (D <= 4096 && O <= 4096) return 25;
  else return 13;                                 // quantized.cpp:85
}
```

against gen 16's 13 / 15 / 13. So on an M5 more shapes stay on the vector path
for longer -- which pushes work *away* from the NAX gemm, not towards it. It
changes which kernel an MTP verify window of 2 to 4 rows picks, and nothing at
M = 1.

**The steel gemm tile.** `GEMM_TPARAM_MACRO` keys off the last letter of the
architecture name and this port instantiates only the "medium device" 64x64x16
/ wm=wn=2 tile (`kernels/steel_gemm_inst.metal`). If an M5 classes differently,
a new tile has to be instantiated or the gemm has no kernel to run.

## 4. The order of work

1. Remove one assert, run `cargo test --release`, and see what mlx picks that
   the port does not carry. The asserts are ordered by how early they bite:
   `quantized.rs` first, `matmul.rs` and `sdpa.rs` after.
2. Re-pin `dispatch_choices_for_this_model` with the gen-17 limits above. It is
   the cheapest true statement about the new part.
3. Re-measure before porting anything. Section 5 lists what does not transfer.
4. Port the prefill path if the numbers say so, in this order: the gated-delta
   chunk 16 kernel, then `quantized_nax` for the gemm, then
   `gather_qmm_rhs_nax`. That is largest-first for this model's shape.
5. `fp_quantized` and `fp_quantized_nax` are a separate decision, not part of
   this one. See HANDOFF, "Metal 4.1, fp8/fp4".

Everything ported keeps the same contract as the rest: `max_abs == 0.0`
against MLX on the same golden references, which on an M5 means regenerating
them on the M5.

## 5. What has to be re-measured, because it is an M4 number

- **Every wall-clock figure**, for the ordinary reason plus a new one: the M4
  numbers were taken on a machine that swapped, and HANDOFF's first item is a
  machine that does not.
- **The bandwidth ceiling.** 465 GB/s sustained of a 546 sticker is this
  part's. So is the CPU-and-GPU-together figure of 516-543 GB/s, and the whole
  co-execution argument built on it.
- **The Rigel verdict on fp8.** "Emulated rather than accelerated, 0.94x of
  fp16" is measured on an M4 Max. The M4 predates the Neural Accelerators that
  arrived with the A19 and M5, so this is exactly the claim least likely to
  survive, and it is the one that decides whether `fp_quantized` is worth
  porting.
- **The schedule model's constant.** `tools/epoch_schedule.py` over-predicts by
  2.4x here, calibrated against one measured reordering. That constant is a
  property of how this GPU overlaps, not of the arithmetic.
- **The 60 us a command buffer costs**, which is what rules out handing the CPU
  a share of a decode step (HANDOFF, "co-execution"). A cheaper boundary would
  reopen that.

## 6. What is not known

- Whether `nax_available()` is even true on the first M5 part that arrives:
  the check is generation >= 17, or >= 18 on a `p` part, and mlx's own comment
  is about macOS and Xcode versions as much as silicon.
- Whether the NAX quantized kernels are bit-exact against the non-NAX ones.
  They will not be -- a different tiling accumulates differently -- so the
  golden references have to be regenerated on the M5 rather than carried over,
  and a reference generated on an M4 will fail there. That is a property of
  the references, not a bug, but it will look like one.
- Whether any of this reaches decode at all. Nothing in sections 2 and 3 says
  it does, and decode is where this port spends 10.4 of its 10.9 ms.
